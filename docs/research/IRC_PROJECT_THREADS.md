# Explicit projects and stable IRC thread identities

Managed IRC now represents an explicit core project with one registered channel and each of its stable threads with its own registered services account and exact persistent nickname. The registry owns project identity and thread membership; workspace equality, display names, navigation groups, and native processes never infer a project. Host and exact workspace scope are verified before membership admission and external IRC work. Each stable thread has one immutable project membership.

The channel is `#km-<slug>-<full project ID hex>`. Its lowercase ASCII descriptive slug is at most 24 bytes, with `project` as the fallback; all 128 project ID bits remain present and total length is at most 61 bytes. The first project journal pins that channel spelling, so a changed descriptive name cannot silently create or adopt another route. The registration owner is the private management account `keelmux-bot`.

Each thread account and nickname is `kt-<base32 of all 128 thread ID bits>`, lowercase without padding, exactly 29 bytes. This is an identity address, separate from a display real name. A format2 full thread/server claim precedes account IO. Generic human account creation cannot use the reserved `kt-` namespace; existing accounts without an original thread claim are never adopted. Each private thread secret contains `account`, `password`, and `nick`, with nick exactly equal to the account. The account journal independently protects its credentials and original registered incarnation.

`ircdchannel.Project` projects ID, HostID, Name, and Workspace from the registry. `EnsureProject(ctx, project, threadID, operationID)` returns a route with ProjectID, ThreadID, Nick, account, private credential reference, endpoint, and registration proof. `BeginProjectChannel` and `ConfirmProjectChannel` use a separate format2 journal keyed by the full project ID. Historical thread channels retain their separate format1 journal and explicit old routing; no route is rewritten or adopted. Historical unaddressed bindings keep their default semantics. The core binding/store contract rejects mixed addressed and unaddressed bindings sharing one channel.

A managed adapter requires the exact expected account and secret nickname before dialing the pinned TLS endpoint. It confirms SASL 900 account identity, the paired 903 target, and exact requested nickname in 001 before JOIN. Ergo's pre-registration placeholder is accepted only as target `*` and mask `*` together, with 903 also targeting `*`; 001 must still confirm the requested stable nick. Mixed placeholders, nick collisions, rewritten welcomes, own nick changes, or account drift fail closed without fallback, takeover, or adoption.

Only channel messages beginning with the exact `nick: text` or `@nick text` address select a thread. The full original text, including the address, remains an authored note. Unaddressed broadcasts, different nicks or case aliases, addresses appearing later in the body, direct messages, and other project channels do not select that binding. Mentions in the body never fan out. The trusted server account tag authenticates the sender; the binding allowlist separately authorizes inbox intake. No terminal input, model turn, approval, or native command derives from inbound text.

Registration and posting mutations remain durably admitted once. Existing project attempts only authorize authenticated read-only registration confirmation; thread accounts reuse their account journal's read-only recovery for admitted mutations. Loss of an acknowledgement never grants a new registration, nickname, account password, or post. A registration permission consumed before an unsuccessful connection or authentication can require manual repair. IRC intake remains bounded live coverage, and disconnections report a history gap.

The source fixture suite covers one exact recipient among two threads sharing a channel, separation of another project's channel, preservation of original authored text, nick/account ambiguity refusal, project identity drift, explicit membership gates, unknown registration without replay, and reserved account ownership. Opt-in owned Ergo tests verify actual TLS/SASL/account journals and registered channel behavior. Integrated executable/native product acceptance and package/customer qualification remain separate evidence gates.
