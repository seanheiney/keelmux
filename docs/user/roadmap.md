# Roadmap and delivery stages

The center stays the same: actual vendor terminals on user-owned machines, stable work and threads, one useful switcher and dependable return. Each expansion needs a runnable journey and exact evidence.

| Stage | Deliverable | Required evidence |
| --- | --- | --- |
| Terminal alpha | Installable native launch/link, switcher/groups, attach/detach, remembered place, owned skills and recovery | Clean-install/upgrade/removal proof, two actual CLIs, stale identity/input rejection and client/daemon recovery |
| Continuity alpha | Verified isolated account/model transitions, checkpoints/outbox, truthful capacity/usage | Actual target identity, exact context/operation outcomes, no duplicated effects, unknown measurement coverage retained |
| Bouncer MVP | Always-on execution homes, one entry to two real servers, canonical shared chat, Mattermost/IRC and optional advice captains | Real server authentication/enrollment, correctly addressed delivery, replay/revocation and no idle model activity |
| Federated beta | Scoped resources, placement, captain coordination and cross-harness/host handoff | Source fencing, partitions, interrupted transfers, destination-local credentials and per-lane authority |
| Personal 1.0 | Dependable declared daily workflow | Published runtime matrix, independent-user simplicity/accessibility, export/rollback and quiet operation |

The current terminal implementation and private entry experiment contribute to these stages. They do not complete every terminal-alpha release gate or the Bouncer MVP. Two local homes are not two independent servers. A local draft is not a chat message. A zero-turn native bootstrap is not authenticated model work.

## Current Codex work

The internal broker explores an owned app-server, exact native thread, durable writer reservation, strict wire policy and scoped observation. Its next product integration is a private home controller separating durable primary process from disposable native UI. Product launch, verified restart/reboot, nonempty history, real prompts, exact callbacks and model/account/usage proof are separate gates.

Native turn submission and consequential external actions in automated acceptance require their own explicit test authorization. A loopback no-auth fixture is used only to prevent inference in controlled tests; it is not a product provider.

## Broader direction

The [full specification](../product/PRODUCT_SPEC.md) retains company/product groups, skills/tools/resources, grouped repair, subscription pools, usage, shared threads, optional captains and supported continuation across models, accounts, harnesses and hosts. Herdr stays conditional on measured lifecycle benefit. Future dedicated graphical clients are native; no product web interface is planned.

Release labels follow actual scope. A complete installable terminal alpha can be useful while deeper broker semantics and federation remain explicit work. Calling an internal prototype shipped would obscure the decisions and recovery limits the operator needs.
